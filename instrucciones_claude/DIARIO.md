# DIARIO — Bitácora compartida de Claudes

> **Qué es esto.** Una bitácora append-only donde cada Claude (el de Santi y el del Fran) deja registro de **qué hizo**, **por qué**, **qué errores se encontraron**, y **qué debería saber el otro**. Sirve para que la próxima sesión (cualquiera de los dos) arranque con contexto real de lo que ya pasó.
>
> **Regla de uso para el Claude que esté activo:**
> 1. Al **arrancar sesión**: leer las últimas ~10 entradas (las más recientes arriba).
> 2. Al **cerrar una tarea no trivial** (feature, bug-fix, decisión arquitectónica, cambio en infra, fix de build, etc.): agregar una entrada siguiendo el formato de abajo.
> 3. **No editar entradas viejas.** Si algo cambió, agregar entrada nueva con "corrección" o "actualización".
> 4. Ordenar por fecha **descendente** (lo más nuevo arriba).
>
> **No es para:** changelogs de usuario, release notes, ni PR descriptions. Eso va a otros archivos.
>
> **Cuándo archivar.** Cuando el archivo supere ~300 entradas, moverlas a `DIARIO-archivo-YYYY-Qn.md` y dejar este vacío.

---

## Formato de entrada

```markdown
## YYYY-MM-DD — <autor: Santi|Fran> — <área: backend|frontend|infra|db|auth|...>
**Qué:** <qué cambió en 1-2 líneas>
**Por qué:** <motivación; requisito / bug / decisión>
**Problemas:** <errores que aparecieron y cómo se resolvieron; omitir si no hubo>
**Impacto para el otro:** <qué necesita saber la otra persona; omitir si no aplica>
**Refs:** <commits, archivos clave, PRs; opcional>
```

## 2026-06-22 (d) — Santi — infra/keycloak (sync idempotente de roles/permisos en cada `up`)
**Qué:** Nuevo `keycloak/sync-roles.sh` + servicio `keycloak-config` en `docker-compose.yml`. Es un init-container (imagen keycloak, corre kcadm y sale) que en **cada `docker compose up`** asegura, de forma **idempotente**, los client-roles (authorities) + realm-roles + sus composites, **sin tocar el resto del realm** (usuarios, clients, settings de login). Resuelve que `start-dev --import-realm` NO re-importe un realm ya existente: este script aplica los roles "por encima" del realm vivo.
**Por qué:** pedido del usuario — al cambiar roles/permisos en el realm JSON, que se apliquen al levantar sin tener que `down -v` (que borra data) ni hacerlo a mano por consola.
**Problemas:** (1) kcadm es lento (spinea una JVM por llamada → ~2-4 min el sync completo); aceptable para un one-shot en background. (2) Mi verificación inicial por `docker exec` falló por **path-mangling de Git Bash** (`/opt/...` → `C:/Program Files/Git/opt/...`); se arregla con `MSYS_NO_PATHCONV=1`. El sync en sí corre DENTRO del contenedor, sin ese problema.
**Verificado:** corrido contra el Keycloak local (no destructivo, acceso3 intacto). kcadm confirma: `SECRETARIA_RM` creado y **VENDEDORA con `books:read/write` + `book_sales:read/write`**.
**Impacto para el otro / notas:**
- En cada `up -d` el one-shot vuelve a correr (re-aplica). Para forzar: `docker compose up -d --force-recreate keycloak-config` o `restart keycloak-config`.
- **Source-of-truth duplicado**: los roles viven en `keycloak/realms/imedba-realm.json` (primer import — crea realm+clients+usuarios) Y en `sync-roles.sh` (re-sync en cada arranque). **Al agregar/cambiar un rol o authority, actualizar AMBOS.**
- **Prod**: el script usa `KEYCLOAK_ADMIN/PASSWORD` (master admin en dev). En prod, el usuario/serviceaccount necesita `manage-realm` + `manage-clients` (más que el `manage-users` del módulo Personal). Documentar al desplegar.
